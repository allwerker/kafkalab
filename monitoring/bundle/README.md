# Kafka monitoring bundle

The portable part of the Kafka Lab: everything needed to monitor **any** Kafka 4.x (KRaft) cluster
with Prometheus-compatible tooling (Prometheus, VictoriaMetrics, Mimir, Thanos). PromQL only, no
lab-specific labels.

| Path | Content |
|---|---|
| `jmx/kafka-jmx-exporter.yaml` | Curated JMX exporter agent config (allowlist, Strimzi-compatible names). Cost of every MBean group: [docs/metrics-performance-impact.md](../../docs/metrics-performance-impact.md) |
| `kminion/` | KMinion values: consumer lag, topic/partition sizes, end-to-end probe via the admin API |
| `scrape/` | Scrape adapters that produce the label contract (below) |
| `dashboards/*.json` | 8 Grafana dashboards (generated by `make dashboards`, folder "Kafka (bundle)") |
| `alerts/kafka-production.yaml`, `alerts/kafka-demo.yaml` | Alerting + recording rules, calm and fast profile, with unit tests (`*.test.yaml`) |
| `catalog.yaml` | Every metric the dashboards and rules use: source and meaning |
| `fixtures/*.prom` | Recorded scrapes the catalog is validated against (`fixtures/record.sh`) |

Runbooks for every alert: [docs/runbooks/](../../docs/runbooks/).

## Label contract

The dashboards and rules rely on exactly these labels. Everything else is optional.

| Label | On | Value | Used for |
|---|---|---|---|
| `kafka_cluster` | every Kafka series (JMX **and** KMinion) | cluster name, identical for brokers and KMinion | `$kafka_cluster` variable, alert grouping |
| `kafka_broker` | broker (JMX) series | KRaft `node.id` | `$kafka_broker` variable, per-broker panels and alerts |
| `namespace`, `pod` | broker series on Kubernetes | as set by the Kubernetes service discovery | joining cAdvisor / kube-state-metrics / kubelet data (Kafka · Pods & Nodes, disk alerts) |
| `topic` | JMX per-topic series | set by the JMX config | per-topic broker metrics |
| `topic_name`, `group_id`, `partition_id`, `broker_id` | KMinion series | set by KMinion | lag, size and probe panels |

The `up` series of the broker targets must carry `kafka_broker` (target labels do), so that
`KafkaBrokerDown` can tell which broker is unreachable.

### Adapters

| Platform | File |
|---|---|
| Strimzi + VictoriaMetrics operator | `scrape/strimzi-vmpodscrape.yaml` (deployed by the lab) |
| Strimzi + Prometheus operator | `scrape/strimzi-podmonitor.yaml` |
| Plain Kubernetes (StatefulSet, Bitnami, CP for Kubernetes …) | `scrape/kubernetes-plain-podmonitor.yaml` |
| VMs / bare metal | `scrape/static-prometheus.yml` (static labels or host-name relabelling) |

Strimzi derives `kafka_cluster` from the pod label `strimzi.io/cluster` and `kafka_broker` from the
pod name suffix (`<cluster>-<pool>-<id>`). KMinion does not know the cluster name: its scrape sets
`kafka_cluster` statically.

## Using the dashboards elsewhere

Import the JSON files (or provision them). Every panel uses the `${datasource}` variable of type
`prometheus`, so pick your Prometheus / Mimir / VictoriaMetrics datasource at the top. Drill-down links
keep the time range, datasource and cluster. Annotations: Grafana annotations tagged `chaos` or
`incident`, and firing alerts from the `ALERTS` series (Prometheus and vmalert write it).

## Using the rules elsewhere

`alerts/kafka-production.yaml` is a plain Prometheus rule file (`promtool check rules` passes).
Labels: `severity` (critical|warning|info), `component` (kafka|consumer|platform), `dashboard`
(dashboard UID); annotations `summary`, `description`, `runbook_url`. The JMX scrape alert assumes a
15 s scrape interval (25 % = 3.75 s) — adjust `ScrapeInterval` in `monitoring/dashgen/internal/rules`
and regenerate if you scrape differently.
